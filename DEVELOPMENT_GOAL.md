# CommandAPI development goal

This document defines the target architecture for CommandAPI.

The current implementation is an intermediate state and may not yet satisfy
all behavior described here. New work should move the implementation toward
this design rather than preserving accidental `/cmd` special cases.

## Responsibilities

CommandAPI is responsible for:

- publishing a command-registration API;
- maintaining the command-provider registry;
- parsing and validating command input;
- executing commands at the declared execution location;
- generating command help, validation, completion, and context presentation;
- presenting command results through RichHudChatAPI when available;
- retaining a vanilla-chat integration when RichHudChatAPI is unavailable.

CommandAPI is not the general chat router when RichHudChatAPI is present.
RichHudChatAPI decides which registered route receives an input submitted
through its interface.

## Startup lifecycle

CommandAPI should start in this order:

1. Publish the CommandAPI immediately.
2. Register CommandAPI's own built-in commands through the same public
   registration path used by external mods.
3. Accept external command-provider registrations at any time.
4. Discover RichHudChatAPI as an optional provider and reconnect when it
   appears after CommandAPI.
5. Wait approximately five seconds before publishing the one-time
   `/cmd help` readiness hint.
6. Send that hint through RichHudChatAPI when it is connected at that time;
   otherwise send it through vanilla chat.
7. If RichHudChatAPI appears later, switch subsequent command output and input
   integration to RichHudChatAPI without repeating the startup hint.

The delay applies only to the readiness hint. API publication and command
registration must not wait five seconds.

## Command providers

A command provider represents one logical mod.

Each provider registration supplies at least:

- stable owner ID;
- display name;
- mod or API version;
- exactly one requested top-level command prefix;
- one or more commands and aliases under that prefix;
- execution-location and permission metadata;
- command handlers.

A provider may register any number of commands under its prefix, but it may not
register a second top-level prefix under the same owner identity.

Examples:

- CommandAPI owns `/cmd`.
- RichHudChatAPI owns `/rhchat`.
- BetterChat may own `/betterchat`.

CommandAPI's built-ins are not hard-coded into the chat adapter. A small
built-in provider registers `/cmd help`, `/cmd status`, and other CommandAPI
commands through the ordinary provider interface.

`/cmd` therefore has no privileged route, parser, companion state, or cleanup
path.

## Prefix conflicts

Top-level prefixes belong to providers rather than forming a silently shared
namespace.

If two providers request overlapping or identical capture prefixes, neither
provider receives automatic priority. The conflict must remain observable.

CommandAPI may detect and report the conflict early, but RichHudChatAPI remains
the routing authority for input entered through its interface. RichHudChatAPI
can reject ambiguous input and let the player or server owner resolve the
effective routes through its routing configuration.

CommandAPI must not select a winner by:

- load order;
- registration order;
- built-in status;
- provider priority;
- longest-prefix preference.

## RichHudChatAPI bridge

When RichHudChatAPI is available, CommandAPI registers chat routes on behalf of
each command provider.

The bridge preserves the original provider identity and version. RichHudChatAPI
must be able to show and configure the actual route-owning mod rather than only
showing CommandAPI as a generic transport.

For every command provider, the bridge may register:

- one input-capture prefix, initially the provider's requested command prefix;
- one context-read prefix, normally `/`;
- one provider-attributed context page generated by CommandAPI;
- one submission callback that returns routed input to CommandAPI.

Although CommandAPI generates and handles the route, the route remains
attributed to the original provider.

This allows RichHudChatAPI to persist entries such as:

    [RichHudChatAPI]
    version = "1.0.0"
    overwrite = false
    context_read = "/"
    input_capture = "/rhchat"

If RichHudChatAPI configuration changes the effective input prefix,
RichHudChatAPI must include the effective route identity or matched prefix in
the submission callback. CommandAPI then parses the command relative to that
effective prefix and dispatches it to the associated provider.

## Context presentation

CommandAPI owns the meaning and presentation of command context pages.

For each provider page, CommandAPI decides:

- command filtering;
- displayed commands and aliases;
- usage and argument hints;
- semantic colors and spans;
- validation messages;
- selected suggestion;
- completion text;
- handling of contextual Up, Down, Tab, and related actions.

RichHudChatAPI renders those generic pages and forwards interactions. It does
not interpret command syntax.

When several provider pages match `/`, RichHudChatAPI displays them through its
context pager. CommandAPI must not assume exclusive ownership of the context
window.

## Input submission through RichHudChatAPI

CommandAPI does not receive every RichHudChatAPI submission and later return a
`sendToOthers` flag.

Instead:

1. CommandAPI advertises provider routes.
2. RichHudChatAPI evaluates all configured routes.
3. RichHudChatAPI dispatches an unambiguous match to CommandAPI's callback for
   that provider.
4. CommandAPI parses and executes the command.
5. Ambiguous or unmatched input is handled by RichHudChatAPI's routing rules.

This keeps the routing table observable and lets RichHudChatAPI explain why a
message was or was not dispatched.

## Vanilla-chat behavior

When RichHudChatAPI is unavailable, CommandAPI may inspect outgoing vanilla
chat messages.

It consumes only messages matching an active command-provider prefix. Unknown
messages remain untouched.

If multiple providers ambiguously match the same vanilla input, CommandAPI
must reject the command and report the conflict rather than choosing a winner.

The vanilla adapter is a fallback integration, not the authoritative router
for RichHudChatAPI input.

## Compatibility and migration

The current API permits multiple prefixes and shared-prefix command
namespaces. Moving to the provider model may require a new API version.

Migration must be explicit:

- preserve the existing API for compatible consumers during a transition;
- add a provider registration contract with one prefix per owner;
- migrate built-ins first;
- migrate RichHudChatAPI's `/rhchat` provider;
- remove all hard-coded `/cmd` route behavior;
- make the RichHud bridge create every provider route through one uniform
  route manager;
- add end-to-end tests using the real RichHudChatAPI router.

Passing mocked endpoint tests alone is not sufficient. The final acceptance
test is in-game routing through the actual RichHudChatAPI provider.

## Acceptance criteria

The target architecture is reached when:

- CommandAPI publishes before any chat integration is required;
- built-in and external providers use the same registration path;
- each provider has one top-level prefix;
- `/cmd` and `/rhchat` use identical route machinery;
- RichHudChatAPI can override effective prefixes without mod changes;
- provider names and versions appear in routing diagnostics;
- ambiguous routes dispatch to nobody;
- vanilla fallback consumes only registered command input;
- late RichHudChatAPI discovery switches future presentation correctly;
- the readiness hint appears once through the best available presentation;
- provider-first and consumer-first startup orders work in game.
